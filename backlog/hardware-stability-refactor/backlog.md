## User Stories

### US-1
- As a Admin operator (authenticated Ultron user managing hardware settings)., I want hardware settings updates must be explicitly user-triggered (no auto-apply on field change), and only one apply operation can execute at a time, so that the workflow remains reliable and traceable.
- Trace: FR-1, AC-1
- Acceptance Criteria:
  - Given an authenticated admin on hardware page, when fields are edited, then no apply request is sent until explicit apply action is triggered.

### US-2
- As a Admin operator (authenticated Ultron user managing hardware settings)., I want the hardware apply pipeline must expose deterministic operation state (`idle|applying|failed|applied`) so UI and logs never leave ambiguous "busy" behavior, so that the workflow remains reliable and traceable.
- Trace: FR-2, AC-2
- Acceptance Criteria:
  - Given one apply operation in progress, when another apply is requested, then system handles it deterministically without stuck-busy state.

### US-3
- As a Ultron privileged helper (root-owned local boundary for hardware operations)., I want integration with Pironman must prioritize stable local control path and avoid long blocking calls in web request lifecycle, so that the workflow remains reliable and traceable.
- Trace: FR-3, AC-1, AC-3
- Acceptance Criteria:
  - Given an authenticated admin on hardware page, when fields are edited, then no apply request is sent until explicit apply action is triggered.
  - Given helper or Pironman timeout/error, when apply fails, then UI receives actionable failure status and system returns to operable idle state.

### US-4
- As a Ultron privileged helper (root-owned local boundary for hardware operations)., I want privileged execution must stay outside web process, with strict local boundary, validated command parameters, and auditable outcomes, so that the workflow remains reliable and traceable.
- Trace: FR-4, AC-5
- Acceptance Criteria:
  - Given security posture validation, when hardware apply executes, then privileged operations are bounded to helper path with auditable logs and no direct web-process privilege escalation.

### US-5
- As a Admin operator (authenticated Ultron user managing hardware settings)., I want every hardware apply request must produce traceable telemetry (request id, duration, result, error cause) for incident diagnosis, so that invalid behavior is handled with deterministic outcomes.
- Trace: FR-5, AC-1
- Acceptance Criteria:
  - Given an authenticated admin on hardware page, when fields are edited, then no apply request is sent until explicit apply action is triggered.
