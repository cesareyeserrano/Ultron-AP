## User Stories

### US-1
- As a Admin operator de Ultron, maintainer de plataforma, y security owner., I want the optional Pironman module must run with explicit feature flag gating and default disabled mode, so that the workflow remains reliable and traceable.
- Trace: FR-1, AC-2
- Acceptance Criteria:
  - Given el feature flag de Pironman esta deshabilitado, when el usuario navega por Ultron core, then no se muestra modulo hardware ni se ejecutan operaciones Pironman.

### US-2
- As a Admin operator de Ultron, maintainer de plataforma, y security owner., I want hardware settings must be applied only by explicit user action and only one apply operation can run at a time, so that the workflow remains reliable and traceable.
- Trace: FR-2, AC-1
- Acceptance Criteria:
  - Given un admin autenticado en el modulo opcional de hardware, when edita valores y presiona Apply, then se ejecuta una sola operacion, el estado transiciona a applied o failed, y la UI nunca queda en busy permanente.

### US-3
- As a Admin operator de Ultron, maintainer de plataforma, y security owner., I want integration must expose capability states `available|unavailable|degraded` and must not block Ultron core when Pironman fails, so that the workflow remains reliable and traceable.
- Trace: FR-3, AC-3
- Acceptance Criteria:
  - Given Pironman API falla o excede timeout, when se solicita read/apply, then la integracion reporta `degraded` o `unavailable` y Ultron core permanece operativo.

### US-4
- As a Admin operator de Ultron, maintainer de plataforma, y security owner., I want privileged operations must remain in helper boundary with strict parameter validation and auditable logs, so that the workflow remains reliable and traceable.
- Trace: FR-4, AC-4
- Acceptance Criteria:
  - Given una solicitud invalida de parametros hardware, when llega al helper, then se rechaza y queda registro auditable del rechazo.
